# Настройки сессии

[English](README.md) · [Русский](README.ru.md) · [Документация](../../README.ru.md)

`SessionOptions` задают, как сессия записывает события и как защищается от переполнения. Передавайте их в `Tracer.Start` или `TracingSession.Start`.

```csharp
Tracer.Start(new SessionOptions
{
    ChunkCapacity = 64 * 1024,
    OverflowPolicy = OverflowPolicy.DropOldest,
    MaxTotalEvents = 5_000_000,
    EnabledCategoryIds = [Tracer.CategoryId("IO"), Tracer.CategoryId("CPU")],
    SampleEveryNGlobal = 10,
    MaxEventsPerSecond = 200_000
});
```

## Буферы и лимиты

| Настройка | По умолчанию | Смысл |
| --------- | ------------ | ----- |
| `ChunkCapacity` | `4_096` | Событий в чанке, не меньше `1_024`. Событие занимает 32 байта, поэтому чанк — это `ChunkCapacity × 32` байт: 128 КБ по умолчанию. Каждый пишущий поток держит как минимум один чанк. |
| `OverflowPolicy` | `DropNew` | Что происходит при достижении лимита: `DropNew` отбрасывает новые события, `DropOldest` перезаписывает самые старые чанки, `StopSession` останавливает сессию. |
| `MaxTotalEvents` | `0` | Лимит событий в сессии. `0` — без лимита. |
| `MaxTotalChunks` | `0` | Лимит чанков. `0` — без лимита. При `DropOldest` лимит действует на завершённые чанки: чанки завершившихся потоков переиспользуются, а живому потоку буфер выдаётся всегда, поэтому сессия может держать до одного чанка на живой поток сверх лимита. |
| `MaxRetentionWindow` | `TimeSpan.Zero` | Хранить только последние N времени по стенным часам; ноль — выключено. Требует `OverflowPolicy.DropOldest` и не может превышать сутки, иначе `Tracer.Start` бросает исключение. Применяется при ротации чанка и при снятии снапшота, но не к чанкам, которыми владеет писатель. См. [Flight recorder](../../guides/flight-recorder/README.ru.md). |

## Фильтрация и sampling

| Настройка | По умолчанию | Смысл |
| --------- | ------------ | ----- |
| `EnabledCategoryIds` | нет | Разрешённые категории, whitelist. |
| `DisabledCategoryIds` | нет | Запрещённые категории, blacklist. |
| `SampleEveryNGlobal` | `0` | Оставлять одно событие из N по всей сессии. `0` и `1` — выключено. |
| `SampleEveryNById` | нет | Словарь `{ id -> everyN }` для точечного sampling. |
| `MaxEventsPerSecond` | `0` | Лимит событий в секунду на поток-писатель. `0` — без лимита. |

Счётчики sampling общие для всей сессии, а не для потока. Потоки-писатели резервируют тикеты из одной глобальной последовательности блоками по 127, поэтому доля сохранённых событий остаётся `1/N` при любом числе потоков, а короткоживущие потоки не сохраняют своё первое событие безусловно. Размер блока взаимно прост с любым практическим `everyN`, за счёт чего границы блоков не совпадают с периодом sampling.

`MaxEventsPerSecond`, в отличие от sampling, действует на каждый поток-писатель отдельно: фактический потолок процесса — `MaxEventsPerSecond` × число пишущих потоков.

## Метаданные

| Настройка | По умолчанию | Смысл |
| --------- | ------------ | ----- |
| `EnableRuntimeMetadata` | `false` | Подмешивать имена, записанные через `Tracer.Id`, в метаданные этой сессии. Значение по умолчанию одинаково в любой конфигурации сборки. Настройка действует только на саму сессию и не регистрирует провайдер глобально. |

Значение по умолчанию можно переключить без кода через host configuration switch `EmberTrace.EnableRuntimeMetadata`:

```xml
<ItemGroup>
  <RuntimeHostConfigurationOption Include="EmberTrace.EnableRuntimeMetadata" Value="true" />
</ItemGroup>
```

## Runtime-счётчики

| Настройка | По умолчанию | Смысл |
| --------- | ------------ | ----- |
| `RuntimeCounters` | `RuntimeCounters.None` | Какие группы метрик рантайма снимать на отдельную дорожку. См. [Runtime-счётчики](../../guides/runtime-counters/README.ru.md). |
| `RuntimeCounterInterval` | `50 мс` | Период сэмплирования, зажимается в [1 мс, 60 с]. |

Runtime-счётчики обходят `EnabledCategoryIds` и `DisabledCategoryIds`.

## Окружение и теги

| Настройка | По умолчанию | Смысл |
| --------- | ------------ | ----- |
| `CaptureEnvironment` | `true` | Записывать настройки машины и рантайма на старте и на остановке. Они сохраняются в файлах `.ember` и позволяют судить, сопоставимы ли две записи. |
| `Tags` | пусто | Пары строк, которые хранятся вместе с сессией, например `arm` и `round` для [сравнения прогонов](../../guides/analysis/README.ru.md#сравнение-наборов-запусков). |

## Обратные вызовы

| Настройка | Вызывается |
| --------- | ---------- |
| `OnOverflow` | Один раз, при первом переполнении. |
| `OnMismatchedEnd` | Когда `Analyze` или `Process` обнаруживает несовпадающий end. |

`OnOverflow` никогда не выполняется на потоке, записавшем переполнившее событие: он ставится в пул потоков, поэтому внутри него безопасно трассировать, брать блокировки и вызывать `Stop()`. Взамен доставка асинхронна и не гарантирует своевременности. Обработчик может быть ещё не вызван к моменту возврата из `Stop()` и может не выполниться вовсе, если процесс завершится раньше. Когда нужен однозначный ответ после окончания сессии, используйте `TraceSession.WasOverflow`. Исключения обработчика подавляются.
